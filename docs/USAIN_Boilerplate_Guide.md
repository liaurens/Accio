# USAIN Tool Architecture & Boilerplate Guide

This document analyzes the `USAIN` tool configuration to identify the "boilerplate" components reusable for other tools generated by the `ToolWizard`.

## 1. Directory Structure

A standard tool follows this directory layout:

```text
<ToolName>/
├── +<ToolName>/            # Main internal package (logic, sub-packages)
│   ├── +inputs/            # Input schema & validation
│   ├── +io/                # Input/Output steps
│   ├── +model/             # Core modeling logic steps
│   ├── +conditions/        # Condition logic for the runner
│   └── DataKeys.m          # Centralized data keys for the Runner
├── +<ToolName>Test/        # Unit and integration tests
├── +<ToolName>Utils/       # Utility classes/functions
├── <ToolName>.m            # Main Class (Entry Point)
├── Contents.m              # MATLAB Help/Documentation info
├── changelog.yml           # YAML-based changelog
├── mkdocs.yml              # Documentation configuration
└── docs/                   # Documentation source files
```

## 2. Main Class Boilerplate (`<ToolName>.m`)

The main class serves as the API entry point and orchestrator. It **must** inherit from `ToolBasis`.

### Core Components
*   **Inheritance**: `classdef <ToolName> < ToolBasis`
*   **Constants**:
    *   `VERSION`: Current tool version.
    *   `TOOL_NAME`: String name of the tool.
*   **Properties**:
    *   `Mdl`: The primary data model.
    *   `Inp`: The input object.
*   **Constructor**:
    *   Standard `varargin` handling using `assign_varargin_2_classprop`.

### Standard Static Methods (Wrappers)
These methods should be present in every tool to provide a consistent interface for users:
*   `copy_inputfiles(targetDir)`: Generates a template input file. Wraps `ToolBasis.copy_inputfiles`.
*   `do_input_checks(inputFilePath)`: Runs validation without full execution.
*   `run(inputFilePath)`: Main execution entry point.
*   `run_batch(inputFilePath)`: Batch execution entry point.
*   `changelog()`: Displays the changelog using `ToolBasis.pprint_changelog`.

### Standard Instance Methods
*   `read_parse_validate_inputfile(Obj, inputFilePath, ...)`:
    *   Orchestrates input loading, expansion, and validation using `usain.inputs.get_schema()`.
    *   Calls `Obj.check_inputlist_with_latest_template`.
    *   Calls `validate.apply_schema_to_inputfile`.
*   `execute_tool(Obj, varargin)`:
    *   **The Orchestrator**. Uses `runner.SequentialRunner` to define the execution flow.
    *   Configures `DataKeys` to pass data between steps.
    *   Adds steps like `LoadExternalFilesStep`, `CrossCheckStep`, `ModelStep`, `WriteFilesStep`.
    *   Returns `OutData` and the object itself.

## 3. Package Internal Boilerplate (`+<ToolName>/`)

### `DataKeys.m`
*   **Goal**: Constants for data exchange within the `SequentialRunner`.
*   **Pattern**: `classdef DataKeys`, containing `properties (Constant)` initialized with `runner.DataKey('Name')`.

### `+inputs/`
*   Should contain the Schema definition (`get_schema.m`) defining valid inputs and defaults.
*   `PostParseManipulations`: For converting units or derived inputs.
*   `PostParseChecks`: For cross-field validation rules (e.g., "start time must be before end time").

## 4. The Runner Pattern

The `USAIN` tool relies heavily on the `SequentialRunner` pattern:

1.  **Define Keys**: in `DataKeys.m`.
2.  **Define Steps**: Classes in `+io`, `+model`, etc., that implement the step interface.
3.  **Compose**: In `execute_tool`, a `Runner` is instantiated, seeded with initial data (Inputs), and populated with a sequence of Steps.
    ```matlab
    Runner = runner.SequentialRunner();
    Runner.set(<ToolName>.DataKeys.Inputs, Obj.Inputs);
    Runner.add( ...
        <ToolName>.io.LoadExternalFilesStep(), ...
        <ToolName>.model.CoreCalculationStep(), ...
        <ToolName>.io.WriteFilesStep() ...
    );
    Runner.run();
    ```

## 5. Metadata Files

*   **`Contents.m`**: Standard MATLAB help file listing available commands (`run`, `copy_inputfiles`, etc.) with hyperlinks.
*   **`mkdocs.yml`**: Configuration for building the tool's documentation site.
*   **`changelog.yml`**: Structured record of changes, used by `changelog()` method.

## Summary of Generalizable Components (The "Wizard" Boilerplate)

When generating a new tool, the **ToolWizard** should generate:
1.  **Folders**: `+NewTool`, `+NewToolTest`, `+NewToolUtils`, `docs`.
2.  **Main Class**: `NewTool.m` with the standard static wrappers and `execute_tool` skeleton.
3.  **DataKeys**: `+NewTool/DataKeys.m` with basic keys (Inputs, Results).
4.  **Contents.m**: Adapted with the new tool name.
5.  **Schema**: `+NewTool/+inputs/get_schema.m` stub.
6.  **Runner Skeleton**: In `execute_tool`.
